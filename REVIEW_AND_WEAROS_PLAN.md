# claude-watch — Codebase Review & WearOS Port Plan

Generated by a multi-agent review workflow (73 agents: subsystem mapping, 4 review dimensions, adversarial verification of every finding, 3 independent port plans + synthesis).

---

## Confirmed findings (52 total, each adversarially verified)

### [CRITICAL] architecture — Single global session token makes the dual-path design (phone + watch both paired) structurally impossible


The bridge keeps exactly one sessionToken (server.js:82; generateSessionToken overwrites it) and nulls the pairing code after the first successful /pair (server.js:970-972), so only the most recently paired device holds a valid token. The README instructs pairing BOTH the iPhone (step 5, code entry) and the watch (Bonjour/manual IP), and both clients independently POST /pair — the watch cannot use the WCSession relay instead, since the watchOS target never activates WCSession and its UI requires direct pairing. Concrete failure: the iPhone pairs first (token A); the watch's first attempt 401s with 'expired' (code was nulled), a new code is generated, and its successful pair issues token B overwriting A. From then on the iPhone's POST /command approvals and SSE reconnects 401. Asymmetric client behavior: the watch hard-unpairs and wipes credentials on 401 (WatchViewState.handleTokenRejected via its SSE delegate and permission-response paths), while the iPhone silently degrades — its SSEClient retries then falls back to polling the unauthenticated /status (which returns 200), so it appears paired but receives no events and all its approvals fail silently (try? swallows the 401). Net effect: only one client can ever be connected; pairing the watch second silently bricks the phone, and re-pairing the phone kicks the watch off with a credential wipe — contradicting the advertised phone+watch architecture. (Additionally, the phone→watch WCSession relay pipeline is send-only dead code, since the watch never registers a WCSession delegate.)

### [CRITICAL] clients — Watch SSE parser has no cross-chunk buffering; events split across TCP reads are corrupted or silently dropped


Finding is accurate as written, with two refinements: (1) the drop is permanent even across reconnects, because handleSSEData updates lastEventId (line 159) from a fragment's 'id:' line before the event-dispatch guard, so the server's Last-Event-ID ring-buffer replay skips the corrupted event; (2) 'the agent hangs waiting' is bounded — the bridge auto-denies the permission after 10 minutes (PERMISSION_TIMEOUT_MS), though the prompt never appears on the watch either way.

### [CRITICAL] correctness — Single malformed Host header crashes the entire bridge (unhandled rejection)


VERIFIED by test. `new URL(req.url, `http://${req.headers.host}`)` sits OUTSIDE the try/catch in onRequest (the try starts at line 1428), and there is no process-level unhandledRejection/uncaughtException handler anywhere. A request whose Host header is not a valid URL host (e.g. raw socket sending `Host: bad host`) makes `new URL` throw; because onRequest is async, this becomes an unhandled promise rejection and Node 22 terminates the process (reproduced: server exited code 1 with `TypeError: Invalid URL`). This is reachable pre-auth by any device on the LAN (server binds 0.0.0.0, line 1448), and when it fires mid-session it kills all PTY sessions and leaves every in-flight PermissionRequest hook hanging in Claude Code. Fix: move the URL parse inside the try, or use `new URL(req.url, "http://localhost")`, and add unhandledRejection/uncaughtException guards.

### [CRITICAL] correctness — PTY spawn uses BSD `script` syntax; every spawned session dies instantly on Linux


PTY spawn in skill/bridge/server.js:265 uses BSD/macOS `script [file] [command...]` syntax with no platform detection or fallback. On Linux (util-linux `script` requires -c/-e for commands), the child exits immediately with 'unexpected number of arguments' (exit 1, reproduced on this machine), so every spawned session emits 'session running' followed instantly by 'session ended'; attachPtyToSession (line 347) and the Codex synthetic-permission PTY re-attach (line 667) fail the same way. Caveat on severity: the README lists macOS 13+ as a prerequisite and the bridge is designed to run on the Mac, where this syntax works — so this is total breakage on Linux but a portability gap rather than a break of the documented macOS configuration. Fix by branching on process.platform (e.g. `script -qec "<cmd>" /dev/null` on Linux with proper quoting) or using a real PTY library like node-pty.

### [HIGH] architecture — Watch SSE parser has no cross-chunk buffering — events spanning TCP chunks are silently dropped


handleSSEData parses each URLSession didReceive(data:) callback independently, splitting the chunk on "\n\n". SSE frames routinely straddle chunk boundaries (any tool-output with a few KB of Bash output, or a permission-request with long questions). A partial block fails the `guard let type, let data` or produces truncated JSON that parseJSON rejects, and the fragment is discarded — there is no lineBuffer like the iOS SSEClient has (SSEClient.swift buffers correctly). Concrete failure: a permission-request event larger than one delivery chunk never renders on the watch; the hook blocks 10 minutes and auto-denies. The project contains two divergent SSE parser implementations (iOS correct, watchOS broken), a trap for both users and any porting effort that copies the wrong one.

### [HIGH] architecture — Hook-to-session attribution by cwd heuristic misroutes events; session_id in the hook payload is ignored


Hook-to-session attribution by cwd heuristic misroutes events; session_id in the hook payload is ignored. resolveHookSession (server.js:1237) matches by exact cwd equality, falls back to the most recent PTY-backed session ignoring cwd (despite a comment claiming 'exactly one'), then auto-creates a slot. Confirmed failures: (1) two Claude sessions in the same directory merge into one watch session with interleaved output and indistinguishable permission prompts — note the decision itself still returns to the correct instance via the per-request permissionId/blocked HTTP response, but the user answers prompts shown under the wrong or merged session context; (2) an external session in ~/projB has all its hooks attributed to a watch-spawned PTY session in ~/projA, so the watch displays projB output and permission prompts under the projA session; (3) auto-created external sessions have no end-of-life — endExternalSession is only triggered by the Codex log monitor, handleHookStop does not change session state, sessions.delete is never called — so external Claude sessions accumulate as permanent 'running' zombies until bridge restart. The proper fix is keying on the session_id already present in every hook payload (binding it to PTY slots on first cwd-matched event) and installing a SessionEnd hook for external session cleanup; mapping Stop to 'ended' would be wrong since Stop fires per turn.

### [HIGH] architecture — Globally installed blocking permission hook hijacks all terminal sessions: 10-minute hang then auto-deny when no client is connected


Globally installed blocking PermissionRequest hook stalls all terminal sessions when no watch client is connected. setup-hooks.sh writes the hook into ~/.claude/settings.json (all projects, no matcher, timeout 600s), and /hooks/permission (server.js:1288-1342) always blocks on waitForPermission (PERMISSION_TIMEOUT_MS = 600s) without ever checking sseClients.size, so with the bridge running and the watch app closed/asleep, every permission prompt in every Claude Code session on the machine silently stalls for up to 10 minutes with no answerable terminal dialog. Because the hook-side and server-side timeouts are both 600s and the hook's clock starts first, the usual end state is hook timeout → fallback to the normal terminal dialog after ~10 minutes (the server's auto-deny typically lands on an abandoned socket); a hard deny reaches Claude Code when the watch responds late. Partial mitigation exists — pending permissions are replayed to SSE clients that connect within the window (server.js ~1190-1216) — but there is no 'no clients connected → return no-decision immediately' escape hatch. The blocking-HTTP design compounds this: req.socket.setTimeout(0) (line 1299) pins the decision on one 10-minute-idle HTTP response with no close-handler cleanup, so if the socket drops mid-wait a later watch approval resolves into a dead response — the watch shows {ok:true} while Claude Code never receives the decision.

### [HIGH] architecture — Port drift between baked-in hook URLs and the bridge's dynamic port range causes silent total failure


Accurate overall, with two minor precisions: the mismatch is not entirely invisible on the bridge side (server.js logs "Port 7860 in use, trying next..." and the banner/Bonjour show the actual bound port), but nothing correlates this with the stale URLs baked into ~/.claude/settings.json, and the hook failures themselves are silent; also, install-mode's destructive filter (line 156) only affects the seven events being installed, while --remove (line 39) affects all events.

### [HIGH] architecture — All bridge state is in-memory; restart forces physical re-pairing, and clients auto-wipe credentials on any transient failure


All bridge state is in-memory (server.js lines 82-121: sessionToken, sessions Map, SSE ring buffer, pendingPermissions, pendingPermissionBodies), so a bridge restart invalidates every client token and forces physical re-pairing with a new 6-digit code from the Mac's terminal — the README documents this as expected behavior. The watch client makes it worse in two ways: (a) on any SSE 401 it auto-wipes stored credentials (handleTokenRejected → bridge.unpair), and (b) WatchViewState.init unpairs after a single failed 3-second /status probe (verifyBridge returns false on any error), so a slow watch Wi-Fi wake or a DHCP-changed bridge IP permanently destroys a still-valid pairing even though the bridge never restarted. The iOS client, by contrast, does not auto-unpair on 401 — it loops between SSE reconnect and polling fallback indefinitely, silently stuck until the user manually unpairs from Settings. Separately, respondToPermission/respondToPermissionWithOption optimistically clear pendingApproval and render "Approved" before the POST completes; if the bridge returns 404 (permission timed out or already resolved) or the request fails at the transport level, the client only logs and never restores the approval UI, so the user believes they approved while the hook-side session blocks until the 10-minute auto-deny. (Note: against a fully restarted bridge the POST 401s, not 404s, and visibly resets to pairing.) Persisting the token across bridge restarts, retrying the init probe before unpairing, and rolling back the approval UI on failure would eliminate these failure modes.

### [HIGH] clients — lastEventId advanced even for events that failed to parse, so dropped events are never replayed after reconnect


In handleSSEData, 'if let id = eventId { lastEventId = id }' (line 159) runs before validating that eventType/eventData were successfully extracted and before JSON parsing succeeds. Combined with the chunk-splitting bug, a truncated block that still contains an 'id: 42' line advances the resume cursor to 42; the reconnect at startEventStream (line 110-112) sends Last-Event-ID: 42, so the bridge never re-delivers the event that was actually lost — permanent loss of approvals/output. Also lastEventId is in-memory only (line 27), so an app relaunch loses the resume position entirely and events during the gap are missed. A port should only commit the event ID after the event has been fully parsed and applied, and should persist it.

### [HIGH] clients — watchOS app never activates WCSession or registers message handlers — the entire iPhone relay path is dead code


watchOS app never activates WCSession or registers message handlers — the entire WCSession relay path is dead code in both directions. WatchSessionManager.activate() is only called from the iOS app (ClaudeWatchApp.swift:10); no watchOS source references WatchSessionManager (the watch uses WatchViewState + direct HTTP/SSE exclusively, and WatchViewState.swift's 'import WatchConnectivity' is unused). Consequently every message RelayService sends — approvalRequestMessage (RelayService.swift:352), batched terminalUpdate (line 692), updateApplicationContext (lines 159/655) — can never be received (no watch-side delegate exists to deliver them), iOS-side isReachable stays false so sends queue via transferUserInfo into a queue that is never drained, and the watch-to-phone path (voiceCommand/approvalResponse handled at line 609) is equally dead. Note: OnboardingView's 'Wi-Fi not required — routes via iPhone' (OnboardingView.swift:65) is not necessarily false, because watchOS transparently proxies URLSession traffic through the paired iPhone over Bluetooth at the system level, so the watch's direct HTTP/SSE connection to the Mac bridge may still work off Wi-Fi — but this happens despite, not because of, the WCSession code. Either wire up WCSession on the watch side or delete the dead relay path.

### [HIGH] clients — SSEClient heartbeat and polling timers are scheduled on a run-loop-less URLSession delegate thread and never fire


resetHeartbeatTimer() uses Timer.scheduledTimer (lines 131-139), which attaches to the current thread's run loop. It is called from handleReceivedData (line 230), which runs on the URLSession delegate queue (session created with delegateQueue: nil at line 105) — a background thread with no running run loop, so the timer never fires. Same for the polling Timer in startPolling (lines 181-188) when reached via handleSSEError on the delegate queue. Also, invalidating a timer from a different thread than the one that installed it (line 132) is undefined per Timer docs. Failure scenario: after the first data chunk arrives, heartbeat-timeout detection is permanently dead; if the TCP connection silently stalls (Wi-Fi roam, laptop sleep), no reconnect ever happens and the phone shows 'connected' forever while receiving nothing. A port must run its keepalive watchdog on a dispatcher/handler that actually executes.

### [HIGH] clients — SSEClient cancel-error feedback loop: reconnects after user disconnect/unpair with stale credentials and inflates failure count


SSEClient funnels URLSession cancellation errors into its failure/reconnect path: stopSSE() (lines 115-127) cancels the live task and invalidates the session, which asynchronously delivers didCompleteWithError(NSURLErrorCancelled) to the delegate (lines 339-341) → handleSSEError (line 299) → recordSSEFailure + reconnectOrFallback, with no intentional-stop flag or cancelled-error filter. Consequences: (1) after disconnect()/unpair() the client reconnects on its own ~1s later — baseURL/token captured in connect() (lines 68-72) are never cleared and unpair is purely client-local (no token revocation), so a zombie SSE connection resumes with stale-but-valid credentials and flips RelayService.connectionState back to .connected after the user unpaired; (2) on heartbeat-timeout and non-200-response reconnect cycles (not on task-completion network errors or graceful stream end, where the task is already complete), the cancel records a spurious extra failure and schedules a duplicate startSSE; the racing startSSE calls cancel each other's tasks, adding further spurious failures, so a single heartbeat timeout can cascade to the maxSSEFailures=3 polling fallback. Fix: an explicit stopped/closed state (or cancelled-error check) in the error path, and clearing credentials on disconnect.

### [HIGH] clients — Polling fallback drops all real events (including permission requests) and is permanent — no recovery back to SSE


poll() (lines 196-219) only GETs /status and emits a synthetic 'poll-status' event; RelayService explicitly ignores it (RelayService.swift:238-240 'just keep alive'). No pty-output, tool-output, or permission-request events are fetched, and lastEventId resume is abandoned. startPolling (lines 177-189) has no logic to periodically retry SSE, so once three failures occur within 30s the client is degraded forever until app restart. Failure scenario: a flaky Wi-Fi minute pushes the client into polling; ten minutes later Claude asks for permission — the phone never shows the prompt, never notifies, and the watch (if relaying through the phone) never hears about it. A port's fallback transport must deliver the same event stream (e.g., poll an /events?since=lastEventId endpoint) and must attempt SSE recovery.

### [HIGH] clients — Approval responses cleared from UI before the network send; failures are swallowed with no retry or restore


Approval responses are cleared from the UI before the network send, and failures are swallowed with no retry or restore. watchOS respondToPermission (WatchViewState.swift:449-494) and respondToPermissionWithOption (403-447) set pendingApproval = nil, mark the session .running, and print '✓ Approved' before issuing the POST; the completion handler only print()s on network error, 404, or non-200, and the watch_pending_permission UserDefaults fallback is removed unconditionally. iOS RelayService.respondToApprovalWithOption (RelayService.swift:361-390) swallows all errors with 'try? await' and calls clearPendingApproval unconditionally; if permissionId is nil it sends an empty string, which the bridge rejects as a 400 (also swallowed). If the send is lost (watch Wi-Fi drop, bridge restart → 404), the prompt is gone with no way to re-answer: SSE Last-Event-ID replay only delivers events newer than the last seen id, and the bridge re-sends only Codex synthetic permissions on reconnect (server.js:1205-1216), not Claude-hook permissions. The agent is not blocked indefinitely — the bridge auto-denies after 10 minutes (PERMISSION_TIMEOUT_MS, server.js:912-922) — but the user's approval is silently inverted into a deny while the watch displays '✓ Approved'. A port should keep (or restore) the prompt until a 2xx ack and surface send failures.

### [HIGH] clients — ApprovalView responds against current global state, not the request it displays — a race can approve/deny the wrong permission


ApprovalView holds the specific 'request' it renders, but respond() (lines 89-108) calls session.respondToPermission/respondToPermissionWithOption, which resolve the target from 'pendingApproval ?? activeSession?.pendingApproval ?? UserDefaults "watch_pending_permission"' (WatchViewState.swift:403-405, 449-451) — i.e., whatever is CURRENT, not the displayed request. handlePermissionRequest overwrites pendingApproval and the UserDefaults key on every incoming request (lines 314-315) and auto-switches activeSessionIndex (line 322). Failure scenario: session B's permission-request arrives milliseconds before the user taps 'No' on session A's sheet → the deny is sent for B's permissionId (with A's option-index semantics), A's request is orphaned, and respondToPermission unconditionally sets the session to .running even on deny (line 458). Responses must be keyed to the permissionId of the rendered request.

### [HIGH] correctness — Hooks are pinned to one port while the server silently falls back through 7860-7869


On EADDRINUSE the server walks to the next port (lines 1459-1470) and happily starts, but setup-hooks.sh bakes `http://127.0.0.1:${PORT:-7860}` into ~/.claude/settings.json (setup-hooks.sh lines 12-13, 93-138). Failure scenario: a stale/orphaned bridge (or anything else) holds 7860; the new bridge binds 7861 and the user pairs with it, but every Claude Code hook — including the blocking PermissionRequest hook — still POSTs to the old instance on 7860, which has no paired watch. Permission prompts never appear on the watch and each one blocks Claude Code for 10 minutes before auto-deny (PERMISSION_TIMEOUT_MS, line 70). Related: the codex-watch wrapper independently hardcodes `${CLAUDE_WATCH_PORT:-7860}` (setup-hooks.sh line 195) and ignores the install-time port argument. The fallback should at minimum warn loudly that installed hooks point elsewhere, or the hooks should discover the port (e.g. a port file).

### [HIGH] correctness — Hook events from other projects are misattributed to the most recent active session


resolveHookSession tries an exact cwd match, then falls back to `findMostRecentActiveSession()` which ignores cwd entirely (lines 1246-1247). Hooks are installed globally in ~/.claude/settings.json, so ALL Claude Code sessions on the machine post to the bridge. Failure scenario: the bridge has a PTY session for ~/proj-a; the user separately runs `claude` in ~/proj-b. Every tool-output, stop, and permission-request from proj-b is tagged with proj-a's sessionId, so the watch shows proj-b's permission prompt under the proj-a session (folderName "proj-a") — the user can approve a Bash command believing it targets a different project. The auto-create branch (lines 1249-1269) is only reachable when no active session exists. The fallback should only apply when cwd is absent, not when it mismatches.

### [HIGH] security — All Claude Code hook endpoints are unauthenticated and bound to 0.0.0.0


The finding is accurate. Two minor refinements: (a) the SSE buffer is a bounded 500-entry ring buffer (line 227), so "SSE buffer exhaustion" is the weakest of the DoS sub-claims — it churns rather than grows unbounded; the genuinely unbounded resources are the sessions Map (phantom sessions are never cleaned up because they have ptyProcess:null and never close a PTY) and open sockets/pendingPermissions held for up to 10 minutes. (b) Scenario 1 is a spoofing/UI-integrity attack, not remote code execution: the forged permission decision is returned to the attacker's own HTTP socket, not to a real Claude Code instance, so an approved 'rm -rf' is not actually executed — but it does inject a legitimate-looking prompt onto the trusted watch UI. The core issue — unauthenticated, LAN-reachable hook endpoints on a 0.0.0.0 bind with no localhost guard, enabling event spoofing, output injection, and resource-exhaustion DoS — is real and reachable.

### [HIGH] security — Plaintext HTTP exposes the bearer token and all terminal output on the LAN


The bridge is created with http.createServer (line 1456), never TLS, and every client sends the session token in cleartext (BridgeClient.swift line 130/209/225 'Bearer <token>', SSEClient.swift line 90). The token is the only credential gating /command and /events, and /command allows approving permission prompts (line 1049) and writing arbitrary bytes into the agent PTY stdin (lines 1145, 1137) as well as spawning sessions in any cwd (line 1020). A passive attacker on the same Wi-Fi (open/shared network) or one performing ARP spoofing sniffs the Authorization header once, then replays it to POST /command with a forged permissionId+decision to auto-approve real tool executions, or injects PTY commands / prompts to the AI agent — i.e. full remote code execution on the developer's machine. Additionally, all streamed pty-output and tool-output (source code, secrets printed by bash commands, file contents) crosses the LAN unencrypted and is readable by any sniffer.

### [MEDIUM] architecture — "Yes, allow all" from the watch direct path silently degrades to a one-time allow; approve/deny semantics are inferred from option position and English label substrings


The bridge supports allowAll → updatedPermissions (server.js:1040), and the iOS client sends it — but the watch path has no allowAll: ApprovalView maps the middle 'Yes, allow all' button to respondToPermission(approved: true) (ApprovalView.swift:101), a plain single allow. Concrete failure: user taps 'Yes, allow all' on the watch, the permission_suggestions are never applied, and the same prompt reappears on every subsequent tool call — inconsistent with the identical button on the phone. The deeper design problem: decision semantics are encoded positionally ('first = allow, last = deny') and by label substring matching ('allow all', "don't ask" in RelayService.swift:377) on both clients, while the bridge separately re-derives Codex option meaning from index/regex (server.js:673). If the bridge or an agent changes option order or wording, an approval can invert into a denial (or vice versa) with no error anywhere. Options should carry machine-readable semantics (e.g., behavior: allow|allow-always|deny) end-to-end.

### [MEDIUM] architecture — No protocol version negotiation; 'sessionId' is semantically overloaded and client contracts already diverge in-repo


The only version signal is a Bonjour TXT record version:'2' that neither client reads; the HTTP/SSE API itself carries no version, and compatibility is handled by duplicating fields ad hoc (sessionId: BRIDGE_ID '// backward compat' in /pair, /status, and TXT). 'sessionId' means bridge instance ID at the top level but per-agent-session UUID inside SSE events — a guaranteed trap for a port. The two Swift clients already disagree on the contract: WatchBridgeClient.PairResponse requires sessionId (non-optional) while iOS BridgeClient treats it as optional; events are parsed as untyped dictionaries with silent `as?` fallbacks, so a renamed field degrades into wrong UI (e.g., every session becomes agent 'claude') instead of an error. Consequence: any bridge change ships blind against three hand-maintained parsers, and old app + new bridge combinations fail in undetectable ways. A single versioned schema (even one shared JSON Schema or a /v1 prefix plus a min-version check at pair time) is missing.

### [MEDIUM] architecture — Discovery stack is fragile: first-result Bonjour with no bridgeId pinning, stored raw-IP URLs, degraded-privacy Wi-Fi requirement, and missing watchOS Info.plist keys


Discovery/pairing stack is fragile in verified, compounding ways: (1) both discovery implementations (BonjourDiscovery.swift:156-167 for iOS, BonjourBrowser in WatchBridgeClient.swift:144-207 for watchOS) accept the FIRST _claude-watch._tcp result that resolves, use the plain .bonjour descriptor so the bridge's advertised bridgeId TXT record (server.js:1486-1493) is never fetched, and never pin any bridge identity — with two Macs running bridges, pairing nondeterministically targets the wrong Mac, producing unexplained 'Wrong code' failures; (2) clients persist raw http://IP:port (WatchBridgeClient.swift:79; RelayService.swift:99-100 bridge_host/bridge_port), and WatchViewState.init wipes stored credentials after a single failed 3-second /status probe at launch — so a DHCP lease change, or even a transient failure (Mac asleep, watch briefly off Wi-Fi), silently unpairs the watch; note reconnects never re-run discovery, so there is no self-healing path; (3) setup documentation (README.md:74) requires users to disable Private Wi-Fi Address per network, a real privacy downgrade, and mDNS still fails under AP client isolation, leaving manual IP entry as the de facto primary path; (4) the watchOS Info.plist lacks NSBonjourServices and NSLocalNetworkUsageDescription while the iOS target has both — an inconsistency worth fixing, though since watchOS does not enforce local network privacy (TN3179), this is unlikely to be the actual cause of on-watch discovery failures. Pinning the advertised bridgeId at pair time and re-resolving via Bonjour on reconnect (or QR pairing embedding host+port+token) would remove most of this.

### [MEDIUM] architecture — Unauthenticated /status leaks project paths and session metadata over cleartext HTTP; bearer token grants arbitrary command injection


The finding is accurate. One minor precision: "passive observer can capture the token" is slightly strong for a switched network, where token capture generally requires active MITM (ARP spoofing) or an open/shared-WiFi segment without client isolation. However, the /status information leak itself (full cwd project paths, session UUIDs, folderName, agent availability, state via getSessionsSnapshot) requires no interception at all — it is directly readable by any unauthenticated LAN peer. The escalation from captured token to arbitrary PTY command injection plus permission auto-approve (allowAll) is confirmed and constitutes effective RCE on the host. Bind to a specific interface, authenticate/trim /status, and add TLS or a Noise-style channel.

### [MEDIUM] architecture — PTY layer is macOS-only ('script' BSD syntax) and command injection is timing-based; SKILL.md docs contradict package.json


PTY layer at skill/bridge/server.js:265 uses BSD/macOS-only `script -q /dev/null <bin> <args>` syntax; on util-linux (Linux) this exits immediately with 'unexpected number of arguments', so sessions never spawn — verified on this host. README documents macOS as the only supported platform, so this is a portability constraint rather than a regression, but the failure is silent to the client: auto-spawn still returns ok:true and the dictated command is dropped without error. SKILL.md:24 falsely claims node-pty is required while package.json contains only bonjour-service (stale docs from an abandoned design). The script wrapper is not a real PTY abstraction (pipes, fixed COLUMNS/LINES, no resize). Separately, auto-spawn command injection (server.js:1135-1140) writes the command after a fixed 500ms setTimeout with no readiness check or retry; claude's TUI usually takes longer to initialize, so first voice commands can be swallowed by startup prompts or mis-timed — a real race, though pty input buffering means it does not fail every time on macOS.

### [MEDIUM] architecture — Codex integration scrapes private log/JSONL formats and resolves approvals by injecting TUI keystrokes


Codex integration scrapes undocumented internal surfaces and resolves approvals by injecting TUI keystrokes. It regex-matches internal tracing lines in ~/.codex/log/codex-tui.log ('ToolCall: exec_command {...} thread_id=' at line 594; 'codex.op="exec_approval" ... codex_core::codex: new|close' at line 837; the literal 'Shutting down Codex instance' at line 847), tails ~/.codex/sessions JSONL files on a 1.5s poll, and answers approvals by writing 'y', '2\n', or ESC into the TUI's stdin (resolveCodexSyntheticPermission, line 660) against a menu whose options the bridge fabricates locally (buildCodexApprovalOptions, line 570) and never verifies against the real TUI. Any Codex release that reformats these log lines silently breaks approval surfacing, and a menu reorder desynchronizes the keystroke mapping. Correction to the worst case: '2\n' is only sent for the user's approval choice and denials always send ESC, so a reorder cannot approve something the user denied; the realistic worst cases are (a) the user's 'Yes, don't ask again' selecting a different or broader menu item, (b) keystrokes landing in the TUI composer if the dialog closed within the 1.5s poll/log-flush window, and (c) for externally detected sessions with no bridge-owned pty, the answer being typed into a freshly spawned 'codex resume' instance (attachPtyToSession, line 343) rather than the user's actual TUI. This subsystem is ~500 of server.js's 1590 lines, so the bridge is not agent-agnostic; a port must replicate or carve out this scraping.

### [MEDIUM] architecture — Zero automated tests across bridge and clients; the cross-device protocol has no executable contract


package.json defines only a start script; there are no test files anywhere in the repo and no XCTest targets in project.yml. The system's riskiest logic — the permission state machine (timeout/allowAll/synthetic-Codex resolution fallthrough in handleCommand), SSE ring-buffer replay, resolveHookSession heuristics, the Codex log regexes, and two independent Swift SSE parsers — is verified only by manually running a Mac + phone + watch. Several findings above (dead relay approval path, watch chunk-parsing bug, allowAll degradation) are exactly the class of defect that a handful of bridge unit tests plus a JSON fixture-based parser test on the clients would have caught; their presence in shipped code is evidence of the gap. For a porting effort this is the first blocker: there is no spec or test suite to validate a reimplementation against, so the port inherits every undocumented behavior of server.js by reading it.

### [MEDIUM] clients — Swipe-dismissing the approval sheet drops the approval with no way to re-open it; one sheet binding per pager page


Swipe/Cancel-dismissing the approval sheet drops the approval with no way to re-open it; one sheet binding per pager page. .sheet(item: $session.pendingApproval) (SessionView.swift:109) means a user-initiated dismissal sets pendingApproval to nil without sending any response. The per-session copy (sessions[idx].pendingApproval) survives but no watch UI ever re-presents it, so the session dot stays amber and the request is unanswerable from the watch: Claude hook permissions stall until the bridge's 10-minute PERMISSION_TIMEOUT_MS auto-deny, and Codex synthetic approvals (which have no timeout) hang indefinitely. Additionally, every SessionView page in MultiSessionPager binds its own .sheet to the same published property; the page-style TabView instantiates its pages, so with 2+ sessions multiple views try to present the same sheet simultaneously, which SwiftUI handles unreliably (prompt may fail to appear). A port should make the approval non-dismissable (or re-present from per-session state) and present it from a single owner.

### [MEDIUM] clients — Single global pendingApproval: concurrent permission requests from multiple sessions orphan all but the newest


Both RelayService (iOS, line 332) and WatchViewState (watchOS, line 314) keep one global pendingApproval that each new permission-request overwrites, while the bridge supports multiple concurrent pending permissions (Map keyed by permissionId, 10-minute timeout each). With two sessions requesting near-simultaneously: on watchOS only the newest is answerable (the sheet is bound to the global, and no UI path can present the older session's stored approval); on iOS it is slightly worse — per-session prompts remain visible, but respondToApprovalWithOption always reads the global approval's permissionId, so tapping the older session's prompt misroutes the answer to the newest request, and after that resolves, the older prompt silently no-ops. The orphaned session stays at .waitingApproval (no permission-cleared event is emitted for hook permissions) until the bridge auto-denies after 10 minutes. Approvals should be queued per session and responses routed by permissionId.

### [MEDIUM] clients — Dictation/voice command lost on network failure while UI shows it as sent with a perpetual thinking cursor


Dictation/voice command lost on network failure while UI shows it as sent with a perpetual thinking cursor. sendVoiceCommand (WatchViewState.swift:509-529) appends the '> text' line and a .thinking indicator BEFORE the fire-and-forget POST; the completion handler only print()s on transport error and never inspects the HTTP status, so bridge-returned errors (401 token rejected, 404 no session, 500 PTY write failure) are silently swallowed as well. If the watch's direct HTTP to the bridge fails (common on watchOS), the transcription is gone — no retry, no queue, no user-visible error — yet the UI shows the command as sent and the thinking cursor persists (removeThinkingLine only runs on subsequent SSE events, lines 183/219). The guard for baseURL/token at line 514 also sits after the UI appends, so an unpaired watch shows the command as sent without any request being made. Note: the companion claim about RelayService.handleWatchMessage(.voiceCommand) (RelayService.swift:618-622, try? with no sessionId → bridge routes to most-recent-active session) accurately describes that code, but it is currently unreachable — the watch app never sends voiceCommand over WatchConnectivity — so it is a latent defect in dead code rather than a live path.

### [MEDIUM] clients — Watch reports 'connected' optimistically before the SSE stream is established and never reflects disconnects


startEventStream sets sessionState.connection = .connected and isReachable = true immediately after task.resume() (lines 119-122), before any HTTP response — if the bridge is down, the UI still shows connected. On stream failure, SSEDelegate.didCompleteWithError (lines 579-592) schedules a reconnect in 3s but never sets connection to .connecting/.disconnected, so during an outage (retrying every 3s indefinitely) the UI and the complication (ComplicationProvider.currentEntry, line 60) show green/Running. ### [MEDIUM] clients — Watch reconnect leaks a URLSession per attempt and can run duplicate concurrent SSE streams


Watch reconnect leaks a URLSession per attempt: every startEventStream call (WatchViewState.swift:115) creates a new URLSession with a strongly-retained SSEDelegate and never invalidates it (stopEventStream at lines 127-130 only cancels the task; no invalidateAndCancel/finishTasksAndInvalidate exists in the watch target, unlike the iOS SSEClient which does invalidate). Since URLSession retains its delegate until invalidated, each 3-second retry during a bridge outage (SSEDelegate.didCompleteWithError, lines 588-591) leaks a session, delegate, and internal delegate queue, accumulating unboundedly on a memory-constrained watch. The originally claimed duplicate-concurrent-stream scenario (init + OnboardingView both starting streams, double-processed events) is not realistically reachable because the two entry points are mutually exclusive behind the isPaired UI gate and the retry path is single-flight, but the missing invalidation still warrants explicit single-flight teardown (invalidate the old session before creating a new one).

### [MEDIUM] clients — Phone-side SSE treats 401 after bridge restart as a generic failure — endless reconnect/polling with a dead token instead of re-pairing


Phone-side SSE treats 401 after bridge restart as a generic failure — endless reconnect then permanent polling with a dead token instead of re-pairing. SSESessionDelegate.didReceive (SSEClient.swift lines 326-332) maps any non-200, including 401 from a restarted bridge whose in-memory token was wiped, to handleSSEError(nil); the client retries with the same stale Bearer token and after 3 failures settles permanently into the polling fallback. The polling fallback's /status endpoint is unauthenticated on the bridge and returns 200 (and poll() ignores HTTP status anyway), so polls silently "succeed" while delivering only poll-status events that RelayService discards — meaning no pty output, permission requests, or session events ever arrive again, and the successful polls mask the auth failure. The watch side handles this correctly by unpairing on SSE 401 (WatchViewState.swift lines 569-586); the iOS side has no 401 handling anywhere outside the pairing flow, so RelayService stays in connecting/degraded limbo and the user sees a stuck app instead of a re-pair prompt. Auth failure must be a distinct path from transient network failure.

### [MEDIUM] clients — Transient network failure at watch app launch permanently erases pairing credentials


WatchViewState.init runs verifyBridge() with a 3-second timeout (lines 31-45, 47-59) and on ANY failure calls bridge.unpair(), which deletes the stored URL and token from UserDefaults (WatchBridgeClient.swift:99-104). watchOS cold launches frequently happen before Wi-Fi is up (radio wakes lazily; bridge Mac may be asleep), so a routine timeout wipes valid credentials and forces the user through the whole pairing-code flow again. Only a definitive 401 proves the token is invalid; unreachability does not. A WearOS port (where the network is similarly not ready at process start) must keep credentials on transient errors and retry.

### [MEDIUM] correctness — Aborted PermissionRequest hook leaves a stale prompt; watch approval silently goes nowhere


handleHookPermission never registers `req.on('close')`, so if Claude Code aborts the hook request (user answers the prompt at the terminal, presses Esc/ctrl-c, or the hook's own 600s timeout fires) the pendingPermissions entry survives up to 10 minutes and no `permission-cleared` SSE event is emitted. Failure scenario: user answers in the terminal, then later taps Allow on the still-displayed watch prompt — resolvePermission succeeds, the server logs `resolved: allow` and writes the JSON response into a dead socket (line 1341); the user believes they approved an action that was never delivered, and if `allowAll` was chosen the updatedPermissions are also lost silently. Cleanup on request close (delete pending entry, clear timer, push permission-cleared) is needed. Also note setup-hooks.sh sets the hook timeout to exactly 600s (line 109) equal to PERMISSION_TIMEOUT_MS, so at timeout the two sides race nondeterministically.

### [MEDIUM] correctness — Pending permission-request can be evicted from the 500-event SSE ring buffer before a disconnected watch reconnects


permission-request events are delivered to offline watches only via Last-Event-ID replay of sseBuffer (lines 1173-1182), but the buffer holds 500 entries and every PostToolUse/PreToolUse hook and PTY output chunk pushes an entry (lines 227-230). Failure scenario: the watch app is backgrounded/out of range; Claude hits a permission request (hook blocks); the session keeps producing tool-output/pty-output events (PTY output alone easily exceeds 500 chunks); the permission-request entry is shifted out; the watch reconnects, replays only surviving events, never shows the prompt, and the hook blocks the full 10 minutes then auto-denies. Pending permissions should be re-synced to new SSE clients the way codexSyntheticPermissions are (lines 1205-1216) — the Claude-side pendingPermissions map has no such sync.

### [MEDIUM] correctness — Pairing silently reopens after success; a re-pair overwrites the session token and unpairs the existing watch


Pairing silently reopens after success: lines 971-972 zero pairingCodeExpiresAt, so any subsequent well-formed POST /pair (valid JSON with a string 'code', within the 5-attempts/5-min rate limit) hits the expiry branch at line 960 and auto-generates a fresh 6-digit code valid for 5 minutes, visible only in the server log. Anyone who can read that log can then pair; generateSessionToken() (line 970) overwrites the single global sessionToken, silently invalidating the existing watch's token — its next request gets 401 with no notification, and there is no 'already paired' guard (README's documented unpair path is a bridge restart). This also extends 6-digit brute-force exposure from a 5-minute startup window to the server's whole lifetime (though impractical at 5 attempts/5 min). Note: the claimed code-rotation DoS is not possible as described — rotation only happens after the current code has expired (at most once per TTL), never while a legitimate user's on-screen code is still valid; spam can only exhaust the shared rate limit (429s). Fix: after a successful pair, require explicit re-pairing intent (restart or console action) instead of auto-regenerating on any /pair request.

### [MEDIUM] correctness — Watch command without sessionId to an external (PTY-less) session throws and returns 500 instead of running the prompt


The PTY-less "run prompt via CLI" branch (lines 1071-1117) is only reachable when the request includes an explicit sessionId. When sessionId is omitted, the fallback `findMostRecentActiveSession() || findMostRecentRunningSession()` (line 1123) can select a hook-created external session whose ptyProcess is null (findMostRecentRunningSession does not check ptyProcess), and line 1145 then dereferences `targetSession.ptyProcess.stdin` → TypeError, caught at line 1148 and returned as an opaque 500 `Cannot read properties of null`. Failure scenario: the only session is one auto-created by hooks from an external Claude (resolveHookSession lines 1249-1264); user dictates a command from the watch without a session selection → 500 error, prompt never runs. The null-PTY branch should be applied to the fallback-selected session too.

### [MEDIUM] correctness — setup-hooks.sh removal matcher deletes unrelated user hooks pointing at any localhost /hooks/ URL


Both the --remove filter (lines 37-48) and the install-time dedup filter (lines 153-159) drop every hook entry containing a URL that merely starts with `http://127.0.0.1:` and contains `/hooks/` — no port or path check tying it to claude-watch. Failure scenarios: (1) a user with their own local automation hook, e.g. `http://127.0.0.1:9000/hooks/notify` under PostToolUse, runs setup-hooks.sh and their hook is silently deleted from ~/.claude/settings.json; (2) because the filter uses `any()` at the entry level, an entry whose `hooks` array mixes one claude-watch hook with user hooks is removed wholesale, destroying the user hooks too. The matcher should require the exact bridge URL prefix (host:port) and filter individual hook objects, not whole entries. Also note the rewrite is non-atomic (json.dump over the original at lines 166-167 and 53-54, no backup/temp+rename), so an interruption mid-write corrupts settings.json, and `$SETTINGS`/`$HOME` are interpolated directly into single-quoted Python source (lines 30, 142), which breaks if the home path contains a quote.

### [MEDIUM] security — Unauthenticated /status leaks absolute working-directory paths and session inventory


handleStatus (routed GET /status at line 1419) has no requireAuth() call and returns getSessionsSnapshot(), which includes each session's absolute cwd, folderName, agent type, plus bridgeId, counts of SSE clients and pending permissions (lines 400-408, 1391-1403). Any LAN host — or any website the user visits, via DNS rebinding since the Host header is unchecked — can GET http://<ip>:7860/status and enumerate every project path/name the developer is working in and confirm the bridge is live and how many agents are running. This is reconnaissance that also feeds the pairing/brute-force and rebinding attacks. The watch client itself relies on /status being unauthenticated for localhost discovery (WatchBridgeClient.swift line 51), so this was left intentionally open.

### [MEDIUM] security — No Host-header validation enables DNS-rebinding to reach unauthenticated endpoints from a browser


No Host-header (or Origin) validation on the 0.0.0.0-bound bridge (server.js: onRequest line 1423, listen line 1448) enables DNS-rebinding/CSRF from a developer's browser to reach the unauthenticated endpoints: GET /status (path/session metadata disclosure), POST /hooks/tool-output and POST /hooks/permission (spoofed SSE events injected into paired watches — readBody at line 179 parses JSON regardless of Content-Type, so even non-rebound simple-request CSRF works for these fire-and-forget POSTs), and POST /pair (rate-limited code brute-force). The genuinely privileged actions — approving permissions / sending commands via POST /command and reading the event stream via GET /events — remain protected by the bearer token (requireAuth), so DNS rebinding cannot directly forge an approval into the agent; the accurate impacts are watch-UI spoofing/injection, /status disclosure, and pairing brute-force.

### [MEDIUM] security — readBody has no size limit — unauthenticated memory-exhaustion DoS


readBody accumulates every request chunk into an in-memory array (chunks.push(c), line 182) with no maximum size before Buffer.concat and JSON.parse (line 185). This runs before any auth check on the unauthenticated endpoints (/pair, all /hooks/*). A LAN attacker (or DNS-rebound browser) can POST a multi-gigabyte body to http://<ip>:7860/hooks/tool-output and drive the Node process out of memory, killing the bridge and any PTY sessions it owns (a control-plane denial of service). There is also no cap on concurrent connections or sessions.

### [MEDIUM] security — Pairing endpoint never locks after pairing; global rate limit allows lockout and token hijack


The pairing endpoint (handlePair, skill/bridge/server.js:937) never refuses requests after a device is already paired: it checks neither sessionToken nor bridgeState. After a successful pair, pairingCodeExpiresAt is set to 0 (line 972), so the next /pair request always passes the expiry check (line 960) and regenerates a valid 5-minute code (line 961), keeping the pairing surface open forever. A subsequent successful pair overwrites the single global sessionToken (lines 139-143), deauthenticating the legitimate watch (requireAuth, line 167) and handing control to the new device. The rate limiter (lines 145-161) is a single global counter with no per-IP tracking, so 5 requests trip RATE_LIMIT_MAX_ATTEMPTS and return 429 to everyone for up to 5 minutes (DoS). The server is exposed on 0.0.0.0 over plaintext HTTP and advertised via Bonjour, so any LAN device can exploit this. Minor corrections to the original finding: pairing-code generation IS logged (not silent), and a wrong code against a still-valid pairingCode does not regenerate the code (only expiry does), so brute force is limited to 5 guesses per 5-minute window against a live code rather than continuous probing of a freshly-minted code. The fix is to gate handlePair so the pairing surface is disabled once a device is paired.

### [LOW] architecture — Client state model duplicated three ways with no snapshot/backlog sync for late joiners


Session/terminal/approval state is independently reconstructed from the SSE event stream in three places (bridge sessions Map, RelayService.sessions, WatchViewState.sessions) with subtly different logic (e.g., the watch auto-switches activeSessionIndex on new sessions and approvals; the phone does not; the phone marks 'ended' via notification, the watch appends a terminal line). A freshly paired or reconnected client receives synthetic 'session running' frames but no terminal backlog (replay requires a Last-Event-ID it does not have), so it shows empty terminals for in-flight sessions; ended sessions are never pruned on the clients and accumulate in the pager UI. A single authoritative snapshot endpoint (sessions + recent lines + pending approvals, which /pair already partially returns but clients ignore) would collapse the three divergent reducers and make consistency testable.

### [LOW] clients — Session activity/elapsed-time state shared across sessions and never reconciled; watch application-context activity is derived from connection only


Session activity/elapsed-time state is shared across sessions and never reconciled in the iOS RelayService, and the WCSession relay path carries connection-derived (and partly dead) state. Verified: (1) currentActivity (RelayService.swift:658-665) maps connected→.running unconditionally, so the SessionState pushed via updateWatchState claims "Running" whenever the SSE link is up — though note the current watchOS app never reads the relayed application context (it connects to the bridge directly and the complication reads local WatchViewState), so this is wrong-but-unconsumed data today. (2) sessionStartDate/elapsedTimer are global (lines 48-49): any one session's "ended" event stops the timer and fires postTaskComplete (471-477) even while other sessions run, and any new session's "running" resets the shared start date (line 459) — this is user-visible in the iOS app today since the bridge supports concurrent sessions. (3) handleTaskComplete (581-588) ignores the event's sessionId and never updates sessions[].activity, so a finished session's status indicator (ConnectionStatusView.swift:205) stays "running" and sendCommand's first-running-session routing (line 396) can pick an idle session. (4) The sessionsUpdate WatchMessage case (WatchMessage.swift:19) is dead code — never sent by RelayService and never handled by the watch, so the relay path cannot carry the multi-session list.

### [LOW] correctness — Dead SSE clients are pruned only on 'close'; write failures are async so the try/catch and heartbeat detection never fire


Dead SSE clients are pruned only on 'close'; the try/catch around res.write() in pushSseEvent (server.js:236-239) and the heartbeat (1221-1224) never fires because write() on a dead/destroyed response returns false rather than throwing (verified on Node 22). If the watch drops off wifi without FIN/RST, heartbeats and events keep buffering into the stale client's unbounded in-memory write buffer (including large pty-output chunks) for the ~15 minutes until Linux TCP retransmission gives up and 'close' finally prunes it. Backpressure (write() returning false) is ignored everywhere. Note: contrary to the original finding, there is no uncaught-exception risk — Node suppresses the async write error when the response is already destroyed — so the impact is limited to dead error-handling code, delayed pruning, and temporary unbounded buffering. Consider handling write()'s false return / 'drain', bounding res.writableLength and destroying laggards, or enabling TCP keepalive on SSE sockets.

### [LOW] correctness — readBody buffers unbounded request bodies on the unauthenticated /pair endpoint


readBody concatenates chunks with no size cap, and /pair (plus all /hooks/* endpoints) accepts POSTs without authentication. The server listens on 0.0.0.0 (line 1448), so any LAN device can stream a multi-gigabyte body to /pair — the rate limiter doesn't help because isRateLimited is checked before the body is read (line 942) and a single request suffices — driving the Node process out of memory and killing the bridge mid-session. Add a byte cap (e.g. 1 MB) in readBody and destroy the request when exceeded.

### [LOW] correctness — pendingPermissionBodies leaks entries when a permission times out or the server never receives a decision


pendingPermissionBodies leaks entries when a permission times out without any decision ever arriving. handleHookPermission stores permission_suggestions in pendingPermissionBodies (server.js line 1306), but the only deletion is in the /command decision path (line 1043). The 10-minute timeout in waitForPermission (lines 914-918) deletes only pendingPermissions, so on a long-lived bridge whose watch is unreachable, each timed-out permission request carrying permission_suggestions orphans one array forever. (Note: late-arriving decisions do clean up via line 1043, and codex synthetic permissions never populate this map, so the leak is limited to the never-answered Claude hook path.) Fix: delete the pendingPermissionBodies entry in the timeout callback as well.

### [LOW] correctness — Ended sessions are never removed from the sessions map


Sessions are added in spawnSession (line 331), touchExternalSession (line 488), and resolveHookSession (line 1264), but nothing ever deletes an entry — killSession and the PTY close handler only set state to "ended". Failure scenario: a long-running bridge with codex scanning (touchExternalSession creates a slot for every recent codex jsonl session) and repeated spawn/kill cycles grows the map without bound; getSessionsSnapshot (returned by /pair and /status, lines 982 and 1396) grows correspondingly and the watch UI receives an ever-longer, mostly dead session list. Prune ended sessions after a grace period.

### [LOW] correctness — Auto-spawn command injection uses a blind 500 ms delay and drops the command silently on slow starts


Auto-spawn command injection is fire-and-forget: handleCommand returns {ok:true, spawned:true} (server.js:1141) before the command is injected via a blind 500 ms setTimeout (lines 1135-1140). If the spawned PTY dies within that window (e.g., `script -q /dev/null <bin>` fails — util-linux script doesn't accept a command operand without -c — or claude exits at startup), slot.ptyProcess is nulled by the close/error handlers and the write is silently skipped, so the watch shows success while the dictated prompt is dropped with no error. Additionally, the unguarded slot.ptyProcess.stdin.write (line 1137) runs with no try/catch and proc.stdin has no 'error' listener, so a write racing the child's death can raise an unhandled stream error (EPIPE) that crashes the bridge process. The "TUI not ready after 500 ms swallows keystrokes" aspect is environment-dependent (pty type-ahead is normally buffered and delivered late), but first-run trust/onboarding dialogs can consume the injected text. Injecting only after the first pty-output (or another ready signal) and reporting injection failure would fix this.

### [LOW] correctness — Notification permission_prompt/idle_prompt events are posted to /hooks/stop and surface as 'stop' on the watch


Notification permission_prompt/idle_prompt events are posted to /hooks/stop and surface as 'stop' on the watch, rendering the session as '— stopped —' with activity .idle. For idle_prompt this is redundant but harmless (the Stop hook already fired). For permission_prompt it is misleading and reachable: the terminal permission dialog (which emits permission_prompt) opens precisely when the PermissionRequest hook path fails while the bridge is still up — e.g. the hook's client-side 600 s timeout expiring before the bridge's identical 600 s auto-deny (Claude's timer starts first), or transient hook-connection failures (the class already observed and partially fixed in commit d37cb4b). A distinct event type or a payload flag (the hook body already carries notification_type, which handleHookStop forwards but no consumer reads) would let the watch show 'waiting on you' (.waitingApproval, which already exists) instead of 'stopped'.

### [LOW] security — Session token stored in UserDefaults instead of the Keychain


Session token stored in UserDefaults instead of the Keychain. The long-lived bridge token is persisted in UserDefaults on both clients (BridgeClient.swift lines 42/93, WatchBridgeClient.swift lines 24/80) rather than the Keychain; no Keychain API is used anywhere in the app. UserDefaults is an unencrypted plist included in device backups and readable with filesystem or backup access; the server never expires or rotates the token, and it grants full bridge control (permission approvals, PTY command injection, session spawning). Additionally, BridgeClient.eventsURL() (line 197) builds an events URL with the token as a ?token= query parameter — this is doubly latent: the server only honors the Authorization header, and eventsURL() is dead code (SSEClient constructs its own URL and authenticates via the Authorization header) — but it should be removed to avoid future accidental use.

## Refuted claims (investigated, found NOT to be real problems)

- **Non-constant-time comparison of pairing code and session token (timing side channel)** — The code facts are accurately described: skill/bridge/server.js:965 uses `code !== pairingCode` and requireAuth (line 167) uses `token === sessionToken`, both ordinary short-circuiting JS comparisons, and the server is LAN-exposed (binds 0.0.0.0, Bonjour-advertised). However, the claimed failure scenario — timing-based recovery of the pairing code or session token — cannot actually occur. (1) Pairing code: /pair is rate-limited to 5 attempts per 5-minute window (RATE_LIMIT_MAX_ATTEMPTS=5, lines 942/953) and the 6-digit code expires and is regenerated after 5 minutes (PAIRING_CODE_TTL_MS); a timing attack needs thousands of samples per candidate to average out noise, but at most ~5 requests are possible per code lifetime, so no timing statistics can be gathered at all. (2) Session token: it is 32 random bytes as 64 hex chars; V8's === does a length check then word-wise (memcmp-style) comparison, so the timing differential per matched word is sub-nanosecond — 3+ orders of magnitude below anything measurable through Node HTTP parsing, event-loop/GC jitter, and even ideal LAN jitter (practical remote timing resolution is microseconds with tens of thousands of samples). Word-granularity comparison also means an attacker must guess ~8 correct hex chars (~4.3 billion candidates) simultaneously to advance the boundary one step — "byte-by-byte" recovery is not even the right attack primitive, and no practical attack recovering a 256-bit token via HTTP timing against a JS string comparison has ever been demonstrated. The finding itself concedes these mitigations ("hence low"). Switching to crypto.timingSafeEqual would be fine defense-in-depth hygiene, but as an actual reachable vulnerability the scenario is theoretical-only, so per the verification standard it is not a real finding.
- **mDNS advertisement discloses machine hostname and bridge ID to the whole LAN** — The factual reading is correct (server.js:1483-1494 does broadcast os.hostname() and BRIDGE_ID in the _claude-watch._tcp advertisement), but this is not a real security defect. (1) LAN-wide advertisement of the service type, host, and port is the intended purpose of the mDNS discovery feature — the watch app browses _claude-watch._tcp to find bridges, so 'target selection' info is disclosed by the feature's existence, not by these fields. (2) The hostname is inherently disclosed by mDNS anyway: bonjour-service defaults the SRV record target to os.hostname().local, so removing machineName from the name/TXT would not hide the hostname from any LAN observer. (3) bridgeId is a per-process crypto.randomUUID() (line 76) with zero authorization value — requireAuth (lines 163-167) checks only the bearer session token — and it is already returned by the unauthenticated GET /status endpoint (lines 1389-1404), so its presence in TXT adds no new exposure. (4) The actual secret (pairing code) is correctly excluded, as the finding admits. There is no reachable failure scenario attributable to these lines that would be prevented by changing them; the only 'fix' would be removing mDNS discovery entirely, i.e., the feature itself. This is standard, intended service-discovery behavior mischaracterized as leakage.
- **Watch-to-phone relay approval path is dead code: taps are silently dropped** — The finding's two factual observations are individually correct — RelayService.swift:350 builds the watch-bound ApprovalRequest without permissionId, and the UserDefaults key "pending_permission_<requestId>" read at line 626 is never written. However, the claimed failure scenario (user taps Yes/No on the watch, tap silently dropped, hook blocks 10 minutes, action auto-denied) cannot occur, because the entire WCSession approval relay is dead on BOTH ends: the watchOS app contains zero references to WCSession or WatchSessionManager (grep of 'ClaudeWatch watchOS/' confirms), so it never receives the phone's .approvalRequestMessage and never sends .approvalResponse — the buggy handler at RelayService.swift:624-635 is unreachable code. Every approval the user can actually tap on the watch arrives via the watch's OWN direct SSE connection to the bridge (WatchViewState.handlePermissionRequest, line 264, which captures the real permissionId and stores it under 'watch_pending_permission'), and the tap POSTs directly to the bridge /command endpoint with that real permissionId (WatchViewState.respondToPermission/WithOption, lines 403-494, invoked from ApprovalView.swift:99-102). That direct path works end-to-end. If the watch is not paired directly to the bridge, ClaudeWatchWatchApp shows OnboardingView — no approval UI exists to tap, so no tap can be dropped. The README's Architecture section also documents the direct path ('watchOS App ... Connects directly to the bridge over Wi-Fi'); only the top ASCII diagram misleadingly shows WCSession as the watch transport. The claim that the app 'cannot approve permissions' from the watch is false; the shipped approval path is the direct one and it is functional.
- **SSE Last-Event-ID replay is broken by per-client sync events consuming buffer IDs, and by counter reset on restart** — The code observations are accurate (handleEvents at skill/bridge/server.js:1190-1216 does mint ids via sseEventId++ for per-client sync frames without buffering them, and the counter/buffer are in-memory), but neither claimed failure scenario is actually reachable. (1) Sync-id consumption cannot cause a client to skip buffered events: pushSseEvent pre-increments so the counter always equals the max buffered id, meaning any sync id a client receives is >= every id in the buffer at that instant; the replay loop (line 1176-1180) is written to the socket before the sync loop in the same synchronous handler, so TCP ordering guarantees the client cannot have recorded a sync id without first receiving all replayed/entitled lower-id events on that connection; and every subsequent real event gets a strictly higher id, is buffered, and passes the `entry.id > lastId` filter on reconnect. Gaps and per-client id divergence are irrelevant to a `>` comparison, and client A never sees client B's sync ids. No sequence loses terminal lines or permission-request replays via this mechanism. (2) The restart scenario is neutralized by the fact that sessionToken (line 82) is also in-memory and only issued in handlePair: after a bridge restart every request 401s until the user manually re-pairs, and the sseBuffer is empty anyway, so there is nothing pre-restart that replay could ever deliver — the counter reset does not suppress otherwise-available replay; a fresh post-restart connection with a stale Last-Event-ID behaves identically to a fresh connection with none. The only residual edge (app process survives restart, user re-pairs in-app, client keeps stale in-memory lastEventId, disconnects again before receiving any new-id frame while an event fires) is a far narrower client-state issue than described, self-heals on the first received frame, and is not caused by the sync-frame id consumption that is the finding's central mechanism. The at-least-once replay guarantee the finding says is broken does in fact hold for live reconnects within a bridge run (modulo the ring-buffer size, which is an inherent, separate limitation).
- **WCSession approval relay broken end-to-end: permissionId stripped when forwarding to watch, and the UserDefaults mapping key is read but never written** — The finding's phone-side observations are factually correct: RelayService.swift:626-627 reads UserDefaults key "pending_permission_<uuid>" that is never written anywhere, and RelayService.swift:350 forwards a new ApprovalRequest with permissionId=nil and a fresh UUID. However, the claimed failure scenario cannot occur because the entire WCSession approval relay is dead code on both ends. (1) No code in the repo ever constructs a .approvalResponse WatchMessage — the only references are the enum definition/codec in Shared/Models/WatchMessage.swift and the pattern-match in RelayService.swift:624 — so the broken handler is unreachable. (2) The watchOS app never receives or displays the forwarded .approvalRequestMessage: the only WCSessionDelegate (WatchSessionManager) is activated exclusively by the iOS target (ClaudeWatchApp.swift:10); the watch app uses WatchViewState, which has no WCSession handling (its WatchConnectivity import is unused). (3) The watch's real approval path is direct-to-bridge HTTP/SSE in WatchViewState.swift — it receives permission requests via SSE, stores its own "watch_pending_permission" key (line 315), and POSTs responses directly to the bridge (lines 405-446) with correct permissionId correlation. Thus "user taps Approve on a WCSession-delivered prompt" is impossible: no such prompt is ever rendered and no approvalResponse is ever sent, so no approval is ever silently dropped in a reachable flow. The finding describes vestigial code that would need permissionId plumbing only if the WCSession relay were ever wired up.
- **WCSession send() can double-deliver messages and mis-reports queued sends as failures; no 65KB payload-size guard** — The finding's failure scenarios cannot occur in this codebase. (1) Duplicate approval submission is impossible: no code ever sends WatchMessage.approvalResponse over WCSession — the watch submits approvals via direct HTTP POST to the bridge (WatchViewState.respondToPermission, ios/ClaudeWatch/ClaudeWatch watchOS/Services/WatchViewState.swift:449-494), and the watchOS target contains zero WCSession/WatchSessionManager references. The iOS-side approvalResponse receive handler (RelayService.swift:624-635) is dead code because the "pending_permission_<uuid>" UserDefaults key it requires is never written anywhere; moreover that key is removed after first use, which would act as an idempotency guard, contradicting the finding's "no idempotency key is checked on receive" claim. (2) The reply-timeout-after-delivery double-send scenario requires a non-nil replyHandler (WCErrorCodeMessageReplyTimedOut only occurs when awaiting a reply); the only two callers of send() (RelayService.swift:352 and :692) pass replyHandler: nil and errorHandler: nil, so errorHandler fires only on genuine delivery failure and no caller is ever "told the send failed" — the manual-retry third-delivery scenario has no code path. (3) The 65KB terminalUpdate loss is moot: the watchOS app never activates WCSession, so these messages are never consumed; the watch gets terminal output by polling the bridge directly (WatchBridgeClient). With no activated counterpart, isReachable stays false and send() takes the transferUserInfo branch anyway, so the sendMessage error path essentially never executes. The remaining points (no activationState check, WearOS chunking advice) are portability/robustness suggestions about effectively vestigial code, not reachable defects.

# Limitations of claude-watch — assessment for a WearOS port

All citations verified against the code at `/home/deck/Development/claude-watch`. Each item is tagged **[inherent]** (a design trade-off you'd have to re-architect to remove) or **[fixable]** (a gap you can close in a port without changing the architecture).

---

## 1. Functional limitations — what it can't do

- **No remote access; LAN-only by construction.** The bridge binds `0.0.0.0` on ports 7860-7869 (`skill/bridge/server.js:63-64, 1448, 1459-1470`) and is discovered only via mDNS `_claude-watch._tcp` (`server.js:1482-1496`). There is no relay server, no tunneling, no push channel. Off the home/office network, the watch is blind. **[inherent]** — the whole product is a same-LAN design.
- **Terminal output is lossy and cosmetic.** PTY output is stripped of ANSI with a naive regex `\x1B\[[0-9;]*[a-zA-Z]` and truncated to 80 chars per line on the watch (`WatchViewState.swift:193-203`); Bash output shows only the first 5 lines; buffers cap at 200 lines/session with 30 displayed (`WatchViewState.swift:217-262`, `SessionView.swift`). You cannot scroll history, view diffs, or read full tool output. **[inherent]** for a watch form factor, but the truncation constants are arbitrary.
- **No real PTY.** Sessions are faked with BSD `script -q /dev/null <bin>` (`server.js:265-275`) — fixed 120x40 dimensions, no resize, no node-pty (`SKILL.md:24` falsely claims node-pty; `package.json` has only `bonjour-service`). Interactive TUI behavior (menus, cursor addressing) is unreliable. **[fixable]** — use node-pty or a proper PTY on the bridge side.
- **AskUserQuestion answers only the first question.** Multi-question payloads lose everything past `questions[0]` (`server.js:1332-1339`). **[fixable]**
- **"Yes, allow all" on the watch is a lie.** The watch's direct path never sends `allowAll`, so `updatedPermissions` are never applied and the same prompt recurs (`ApprovalView.swift:89-108` vs bridge support at `server.js:1040-1043`). Only the iOS path sends it (`RelayService.swift:377`). **[fixable]** — a WearOS port should send `allowAll: true`.
- **Approve/deny semantics are positional and English-substring-based.** "Last option = deny", label matching on "allow all"/"don't ask" (`WatchViewState.swift:467`, `RelayService.swift:377`, and independently on the bridge for Codex at `server.js:673`). A wording or ordering change can invert approval into denial silently. **[fixable, but requires a protocol change]** — options should carry machine-readable `behavior` fields.
- **Voice input is not speech recognition.** `VoiceInputView` is a TextField relying on the system keyboard/dictation; `SpeechService` is vestigial. Fine for a port (WearOS has equivalent IME dictation), but there's no streaming-voice or push-to-talk design to copy. **[inherent to watch platforms]**
- **Commands to external (hook-created) sessions are one-shot, not interactive.** Sessions auto-created from hooks have no PTY; watch commands run `claude -p <text> --continue` in that cwd (`server.js:1079-1116`) — a *new* headless turn, not input to the user's live terminal. **[inherent]** — there is no way to inject stdin into a terminal the bridge didn't spawn.
- **Codex support is log-scraping, not an API.** ~500 of 1590 bridge lines regex-match `~/.codex/log/codex-tui.log` tracing lines and tail session JSONL on a 1.5 s poll, then answer approvals by typing `y` / `2\n` / ESC into the TUI stdin against a menu the bridge fabricates and never verifies (`server.js:570-686, 796-899`). Any Codex release can silently break it. **[inherent to the approach]** — a port should treat Codex support as optional/fragile.
- **The phone-relay path is dead code.** The watchOS target never activates WCSession (`ClaudeWatchWatchApp.swift:28`; unused import at `WatchViewState.swift:2`); the phone's approval-response handler reads a UserDefaults key nothing writes and forwards `ApprovalRequest`s with a fresh UUID and no permissionId. **Good news for WearOS: the direct HTTP/SSE protocol is the only real protocol** — you can ignore WCSession/WatchMessage entirely and don't need a phone app at all.

## 2. Environmental / deployment constraints

- **macOS-only bridge.** The `script` invocation uses BSD syntax; on util-linux every spawned session dies instantly with "unexpected number of arguments" (verified on this machine; `server.js:265`). README requires macOS 13+ (`README.md:251-260`). **[fixable]** — branch on `process.platform` or use node-pty; matters if your dev machine is Linux.
- **Bonjour fragility is the de facto onboarding path.** First-result discovery with no bridgeId pinning (TXT record is advertised at `server.js:1486-1493` but never read by any client), 5 s timeout, resolution via a throwaway TCP connection (`WatchBridgeClient.swift:144-207`). mDNS fails under AP client isolation; README tells users to disable Private Wi-Fi Address (`README.md:74`). Manual IP entry + port scan 7860-7869 is the real-world fallback. WearOS adds NSD/mDNS quirks of its own (multicast lock required, Doze throttling). **[partly inherent]** — pin bridgeId at pair time and consider QR pairing embedding host+port+token.
- **Hooks are pinned to port 7860 while the bridge floats.** `setup-hooks.sh:12-13` bakes `http://127.0.0.1:${PORT:-7860}` into `~/.claude/settings.json`; the bridge silently falls through 7860→7869 on EADDRINUSE (`server.js:1459-1470`). A stale process on 7860 (or Gradio, which defaults to 7860) means every hook — including the blocking PermissionRequest — posts to the wrong instance and each prompt hangs 10 minutes. **[fixable]** — port file or loud warning.
- **Hooks are global and blocking.** Installed machine-wide with no matcher (`setup-hooks.sh:89-140`); every Claude Code session on the machine stalls up to 600 s per permission prompt when the bridge is up but no watch is connected — the bridge never checks `sseClients.size` before blocking (`server.js:1288-1342`). Hook timeout == bridge timeout (600 s both) so timeout behavior races nondeterministically. **[fixable]** — fast no-decision return when no client is connected.
- **No daemon management.** Bridge is started manually (`node server.js`); no launchd/systemd unit, no auto-restart. **[fixable]**
- **No TLS anywhere.** Plain `http.createServer` (`server.js:1456`). See security.

## 3. Reliability limitations

- **All bridge state is in-memory; restart = re-pair.** Token, pairing code, sessions Map, 500-event ring buffer, pending permissions (`server.js:82-121`). A bridge restart 401s every client and forces physical proximity to read a new console code. **[inherent to the current design, fixable with a persisted token file]** — for a WearOS port, expect frequent re-pairing unless you fix the bridge too.
- **The bridge crashes on one malformed request.** `new URL(req.url, http://${req.headers.host})` sits outside the try/catch in `onRequest` (`server.js:1423`, try begins ~1428); an invalid Host header is an unhandled async rejection that kills the process (verified, exit 1) — taking down every PTY session and hanging in-flight permission hooks. Reachable pre-auth from any LAN device. **[fixable, one-liner]**
- **Permission prompts can be lost forever.** Pending Claude-hook permissions are delivered to reconnecting clients only via Last-Event-ID ring-buffer replay; 500 entries of pty-output easily evict a permission-request before the watch reconnects (`server.js:227, 1173-1182`). Only Codex synthetic permissions are re-synced on connect (`server.js:1205-1216`). **[fixable]** — re-sync `pendingPermissions` on SSE connect; a WearOS port should also request a pending-permission snapshot.
- **Aborted hooks leave zombie prompts.** No `req.on('close')` handler in `handleHookPermission` (`server.js:1311`); if the user answers in the terminal, the watch prompt persists and a later tap "succeeds" into a dead socket.
- **The watch SSE parser drops events spanning TCP chunks.** `handleSSEData` splits each `didReceive` chunk on `\n\n` with no cross-chunk buffer (`WatchViewState.swift:134`), and commits `lastEventId` *before* validating the event (`:159`), so a large permission-request is not only dropped but never replayed. The iOS `SSEClient` buffers correctly — **do not port the watchOS parser**. **[fixable; critical porting trap]**
- **Optimistic UI everywhere.** Approvals clear the prompt and show "Approved" before the POST; failures/404s are swallowed (`WatchViewState.swift:449-494`, `RelayService.swift:361-390` with `try?`). Voice commands echo "> sent" before the network call and never inspect HTTP status (`WatchViewState.swift:509-529`). Net effect: user's approval can silently become a 10-minute auto-deny while the UI says approved. **[fixable]** — ack-gated UI in the port.
- **Credential auto-wipe on transient failure.** `WatchViewState.init` unpairs on a single failed 3 s `/status` probe (`WatchViewState.swift:38-59`), and any SSE 401 hard-unpairs. A DHCP change or slow radio wake dest­roys a valid pairing. Reconnect never re-runs discovery, so no self-healing. **[fixable; critical for WearOS]** — networks are not ready at process start; keep credentials on transient errors, unpair only on definitive 401.
- **iOS-side degraded modes never recover.** SSE reconnect is fixed 1 s (no backoff); 3 failures in 30 s trips a one-way polling fallback of `/status` every 2 s whose events RelayService discards — so no output/permissions ever arrive again (`SSEClient.swift:156-219`, `RelayService.swift:238-240`). Heartbeat/polling Timers are scheduled on a run-loop-less delegate queue and never fire (`SSEClient.swift:131-139`). These are iOS bugs, but they are a **catalog of what to design correctly** in a WearOS port: real backoff, a fallback that carries the actual event stream, and a keepalive watchdog on a live handler.
- **Backgrounding kills the stream.** iOS declares `fetch`/`remote-notification` background modes but registers no BGTask and no APNs; SSE and all timers suspend when backgrounded (`Info.plist:29-33`). WearOS Doze/App Standby is even more aggressive — **plan for a foreground service or `WorkManager`/data-FCM wake, because a naked SSE socket will not survive backgrounding.** **[inherent platform constraint you must design around]**
- **Ended sessions never pruned.** Neither the bridge Map (`server.js:331` and elsewhere; only state set to "ended") nor the clients evict dead sessions, so `/status`, `/pair` snapshots, and the pager grow unbounded on a long-lived bridge (worsened by Codex `touchExternalSession` creating a slot per recent JSONL). **[fixable]**

## 4. Security limitations

- **No TLS — token and all output in cleartext.** `http.createServer` (`server.js:1456`); the bearer token rides in the `Authorization` header on every `/command` and `/events` call. A sniffer on open/shared Wi-Fi (or via ARP spoofing on a switched LAN) captures the token, then replays it to `POST /command` to inject arbitrary bytes into the agent PTY stdin (`server.js:1145`), auto-approve permissions with `allowAll` (`server.js:1040`), or spawn sessions in any cwd — **effective RCE on the dev machine.** All source code, secrets, and file contents in pty-output/tool-output also cross the LAN in clear. **[inherent to the current design; the single most important thing to fix in a port + bridge]**
- **Hook endpoints and `/status` are unauthenticated on a 0.0.0.0 bind.** `/hooks/*`, `/pair`, `/status` require no auth (`server.js:163-168` guards only `/command` and `/events`). Any LAN peer can spoof `permission-request`/`tool-output` SSE events onto the trusted watch UI, or enumerate every project's absolute cwd, folderName, agent list, and session count via `GET /status` (`server.js:1389-1404`). **[partly inherent]** — the hooks are unauthenticated *by design* because Claude Code calls them from localhost, and the watch's localhost discovery relies on `/status` being open (`WatchBridgeClient.swift:51`). A port can't fix this alone; it needs a bridge that adds a localhost guard / Host validation.
- **DNS-rebinding / CSRF.** No Host or Origin validation (`server.js:1423`); `readBody` parses JSON regardless of Content-Type (`server.js:179`), so a developer's browser visiting a malicious page can hit `/status`, `/hooks/*`, and `/pair`. Privileged `/command`/`/events` stay token-protected. **[fixable on the bridge]**
- **Unbounded `readBody` = pre-auth memory-exhaustion DoS.** `chunks.push(c)` with no cap before `Buffer.concat`/`JSON.parse` (`server.js:179-185`), reachable on unauthenticated `/pair` and `/hooks/*`; rate limit is checked before the body is read. A single multi-GB POST OOMs the bridge. **[fixable]** — add a byte cap.
- **Pairing never locks after success.** `pairingCodeExpiresAt` is zeroed on success (`server.js:971-972`), so any later `/pair` regenerates a fresh 5-min code; a successful re-pair overwrites the single global token, silently deauthenticating the current device (`server.js:139-143`). The rate limiter is one global counter (no per-IP), so 5 requests 429 everyone. **[fixable]** — gate pairing behind explicit intent once paired.
- **Token stored in plaintext UserDefaults, never rotated/expired** (`BridgeClient.swift:93`, `WatchBridgeClient.swift:80`). On WearOS use EncryptedSharedPreferences/Keystore. **[fixable]**

## 5. Scaling / multi-session limits

- **Single global token → phone + watch cannot both be paired.** The bridge keeps exactly one `sessionToken` and nulls the pairing code after the first `/pair` (`server.js:82, 970-972`). The README tells users to pair *both* the iPhone and the watch, but the second pair overwrites the first's token — whichever paired last wins; the other silently 401s. **This is the deepest architectural limit.** For a WearOS port it means: **one client at a time, period**, unless you redesign the bridge to issue multiple tokens. Good news: if you drop the phone entirely and go watch-direct, this is a non-issue. **[inherent — requires bridge redesign for multi-client]**
- **Hook-to-session attribution is a cwd heuristic that misroutes.** `resolveHookSession` matches exact cwd, else falls back to the most-recent active PTY session *ignoring cwd*, else auto-creates a slot (`server.js:1237-1270`). Claude Code's own `session_id` (present in every hook payload) is ignored. Consequences: two sessions in the same directory merge; an external session in projB has its prompts shown under projA's session — **a user can approve a Bash command believing it targets a different project.** **[fixable]** — key on the hook payload's `session_id`.
- **External sessions are permanent zombies.** No SessionEnd hook is installed; `handleHookStop` doesn't change session state (Stop fires per-turn, so mapping it to "ended" would be wrong); `sessions.delete` is never called. External Claude sessions accumulate as "running" until restart. **[fixable]** — install a SessionEnd hook.
- **One global `pendingApproval` per client.** Both clients overwrite a single pending approval on each new request (`WatchViewState.swift:314`, `RelayService.swift:332`), while the bridge supports N concurrent pending permissions keyed by permissionId. With two near-simultaneous requests, only the newest is answerable; older ones orphan until the 10-min auto-deny, and on iOS the response can misroute to the wrong permissionId. `ApprovalView` also resolves against *current* global state, not the request it renders (`ApprovalView.swift:98`), so a race can approve/deny the wrong permission. **[fixable; important for a correct port]** — queue approvals per session, route responses strictly by permissionId.
- **No protocol versioning.** The only version signal is the Bonjour TXT `version:"2"`, which no client reads (`server.js:1490`). `sessionId` means *bridge instance ID* at the top level but *per-agent-session UUID* inside SSE events — a guaranteed porting trap. Events are parsed as untyped dictionaries with silent `as?` fallbacks (a renamed field becomes wrong UI, e.g. every session decodes as agent "claude"). The two Swift clients already disagree (`PairResponse.sessionId` required on watch, optional on phone). **[fixable]** — define a versioned schema and a min-version check at pair time.
- **Zero automated tests; no executable spec.** `package.json:7` has only a `start` script; no test files, no XCTest targets. The riskiest logic (permission state machine, ring-buffer replay, `resolveHookSession`, Codex regexes, two divergent SSE parsers) is verified only by manual Mac+phone+watch runs. **For your port this is the first blocker: there is no contract to validate a reimplementation against — you inherit every undocumented behavior of `server.js` by reading it.** **[fixable, and should be your first deliverable]**

## Porting guidance (bottom line)

**Target the HTTP/SSE protocol directly and skip the phone.** The watch-direct path (Bonjour → `POST /pair` → bearer token → `GET /events` SSE + `POST /command`) is the only real protocol; WCSession/WatchMessage is dead code you can delete.

**Inherent constraints you must design around (not bugs):** same-LAN only, no push/remote, in-memory bridge state (re-pair on restart), single-client token model, watch-form-factor output truncation, log-scraping Codex support, and aggressive background suspension (design a foreground service, don't rely on a bare socket).

**Fixable gaps you should fix in the port (and ideally upstream in the bridge):**
- Cross-chunk SSE buffering with `lastEventId` committed *only after* successful parse, persisted across launches (avoid the `WatchViewState.swift:134/159` trap; copy the iOS `SSEClient` buffering model instead).
- Ack-gated approval/command UI (no optimistic "Approved"); keep the prompt until a 2xx.
- Per-session approval queue, responses routed by `permissionId`; send `allowAll` for "allow all".
- Keep credentials on transient network errors; unpair only on definitive 401.
- Real reconnect backoff and a fallback transport that actually carries the event stream.
- Encrypted token storage (Keystore/EncryptedSharedPreferences).
- Re-sync pending permissions on connect (request a snapshot; the bridge only re-syncs Codex ones today).

**Fixes that require touching the bridge (`server.js`), not just the client:** TLS or an authenticated channel, localhost guard + Host-header validation, `readBody` size cap, the `new URL` crash (`server.js:1423`), Linux `script`/node-pty portability, port-drift between hooks and the bound port, session attribution by `session_id`, multi-token support if you want phone+watch, ended-session pruning, and a versioned schema. If you can only change the client, TLS/auth/RCE exposure and the single-token limit remain.

Key files: `/home/deck/Development/claude-watch/skill/bridge/server.js`, `/home/deck/Development/claude-watch/skill/setup-hooks.sh`, `/home/deck/Development/claude-watch/ios/ClaudeWatch/ClaudeWatch watchOS/Services/WatchViewState.swift`, `/home/deck/Development/claude-watch/ios/ClaudeWatch/ClaudeWatch watchOS/Services/WatchBridgeClient.swift`, `/home/deck/Development/claude-watch/ios/ClaudeWatch/ClaudeWatch watchOS/Views/ApprovalView.swift`, `/home/deck/Development/claude-watch/ios/ClaudeWatch/ClaudeWatch iOS/Networking/SSEClient.swift`.

## 3. Synthesized plan: "Hardened-Bridge Standalone Wear Client, Relay-Ready"

**Architecture:** unchanged wire concept (HTTP + SSE + multiplexed POST /command), but bridge v3 fixes all confirmed defects behind a `/v1` prefix + TXT `v:3`, with the legacy surface kept frozen for the existing iOS/watchOS apps. One Gradle project: `:shared` (protocol models, formatters, ring buffer — kotlinx.serialization), `:wear` (Compose for Wear OS + Horologist, standalone=true), `:phone` (empty until Phase 6). Watch talks directly to the bridge via OkHttp/okhttp-sse inside a `connectedDevice` FGS; approvals are high-importance notifications with actions + RemoteInput; discovery ladder is NsdManager-over-real-Wi-Fi → unicast `/ping` probe through the BT proxy → manual IP.

### Phase 0 — Bridge hardening + executable protocol contract (~1 week, parallelizable with Phase 1)
**Deliverable (testable):** `node --test` suite green in CI covering every fix below via recorded hook fixtures; existing iOS/watchOS apps still pass a manual smoke test against the same bridge.
Fixes folded in (all from the confirmed list), in `skill/bridge/server.js` refactored into modules (`hooks.js`, `sessions.js`, `permissions.js`, `codex.js`, `transport-sse.js`, `credentials.js`):
1. **Crash:** move `new URL(req.url, ...)` inside try (or base `http://localhost`); add `process.on('unhandledRejection'/'uncaughtException')`.
2. **DoS:** 1 MB cap in `readBody` with `req.destroy()`; bound SSE client `res.writableLength` and destroy laggards; TCP keepalive on SSE sockets; prune ended sessions after a grace period; delete `pendingPermissionBodies` in the timeout callback.
3. **Auth/exposure:** enforce `remoteAddress` loopback on `/hooks/*`; authenticate `/status`; add minimal unauthenticated `GET /ping` `{proto, bridgeId, machineName}` (this is what discovery probes); validate Host header against localhost + the bound LAN IP (kills DNS rebinding).
4. **Pairing/tokens (fixes the architecture-critical single-token bug):** per-device tokens, SHA-256-hashed, persisted to `~/.claude-watch/credentials.json` (0600); pairing surface locks after success and reopens only via explicit console action/flag; restart no longer unpairs anyone. (Plan C's design, minus TLS-blocking scope — TLS with pinned self-signed cert is a fast-follow flag, cleartext allowed for v1 via the client's `networkSecurityConfig` scoped to RFC1918.)
5. **Attribution:** key sessions on the hook payload's `session_id`, cwd match as fallback only when session_id absent; install a SessionEnd hook for external-session cleanup; never fall back to "most recent active" on cwd mismatch.
6. **Permission reliability:** `req.on('close')` on `/hooks/permission` → delete pending entry, emit `permission-cleared`; re-send *all* pending Claude permissions to newly connected SSE clients (the codexSyntheticPermissions treatment) so ring-buffer eviction can't lose a prompt; if zero SSE clients are connected, return no-decision immediately instead of blocking 600 s.
7. **Semantics:** permission options carry machine-readable `behavior: allow | allow-always | deny` end-to-end (no more label-substring/position inference); forward `notification_type` so clients can render `waitingApproval` instead of "stopped".
8. **Ops:** write the actual bound port to `~/.claude-watch/port`; setup-hooks.sh reads it and its removal matcher filters individual hook objects by exact bridge URL, with atomic temp+rename writes; PTY spawn branches on `process.platform` (`script -qec` on Linux) or moves to `node-pty`; auto-spawn injects the command after first `pty-output` instead of a blind 500 ms timer, with guarded stdin writes.
