# Bridge Architecture

The wire contract for watch clients (endpoints, SSE event catalog, permission
semantics, versioning rules) lives in [PROTOCOL.md](PROTOCOL.md); its
executable form is the recorded fixture corpus in `test/fixtures/`, replayed
by `test/protocol-fixtures.test.js`. This document describes the bridge's
internals and policies.

## Module map

| Module | Responsibility |
|---|---|
| `server.js` | Entry point: routes table, `/v1` prefix normalization, Host-header check (via `host-guard.js`, runs pre-auth on every route), process-level crash guards (`unhandledRejection`/`uncaughtException` log instead of dying), port binding, port-file publication (writes the actual bound port to `~/.claude-watch/port` on startup — the single source of truth the Zed-launched `claude-agent-acp` fork reads to find its uplink; removed on graceful shutdown only if it still records this instance's port), pairing banner, Bonjour advertisement, graceful shutdown. |
| `util.js` | Shared low-level helpers: `log()` (with the #93 dead-sink fallback: once a stdout/stderr write fails — `logSinkFailed()`, fed by the stream 'error' silencers in `server.js` — lines append to `~/.claude-watch/bridge.log` and `isLoggingDegraded()` surfaces it in `/v1/status`), `jsonResponse()`, `readBody()` (1 MiB body cap: oversized requests get a 413 and a destroyed socket before auth runs — the cap constant lives here because this module must not import `config.js`), `isLoopbackAddress()`. No bridge-module imports. |
| `host-guard.js` | `createHostAllowList()`: the Host-header allow-list behind the DNS-rebinding guard — static entries (localhost/loopback, `10.0.2.2`, operator additions) plus the machine's interface addresses, re-snapshotted on a Host miss (throttled) so an IP change mid-run self-heals. No bridge-module imports. |
| `config.js` | Configuration constants, `BRIDGE_ID`, and `claude`/`codex` binary discovery (logs at startup). `BRIDGE_ID` is generated once and persisted to `bridge-id` next to `credentials.json`: clients pin it at pair time and verify it on every reconnect preflight (the wrong-Mac guard), so — like the bearer tokens it travels with — it must survive restarts; a per-process id would strand every paired client in a terminal "different bridge" state after any routine restart. |
| `credentials.js` | Per-device token store (SHA-256 hashes persisted to `credentials.json`), pairing-code generation/validation, pairing lockout latch, `requireAuth()`, bridge state. |
| `rate-limit.js` | Per-IP pairing rate limiter (fixed window per remote address, expired windows pruned on every call). |
| `transport-sse.js` | SSE event ring buffer, connected clients, `pushSseEvent()` broadcast (evicts clients whose response write buffer exceeds `SSE_MAX_BUFFERED_BYTES`), and the `GET /events` handler (Last-Event-ID replay, connect-time snapshot — recent terminal backlog for fresh clients plus registered sync providers on every connect — heartbeat, TCP keepalive on the socket). Event ids are wall-clock-seeded so they stay monotonic **across bridge restarts**: tokens and client replay cursors both survive a restart, so a reset id space would silently mask the entire post-restart backlog behind the client's old cursor. |
| `permissions.js` | The shared pending-permission core: the blocking `waitForPermission()` / `resolvePermission()` / `cancelPermission()` trio, plus the canonical machine-readable option semantics (`PERMISSION_BEHAVIORS`, `canonicalPermissionOptions()` — see "Permission decision semantics" below). Prompts are raised by the ACP lane (`acp.js`) and the Codex synthetic menu (`codex.js`). Every non-answer exit — expiry, a request settled elsewhere and canceled — funnels through `voidPermission()`, which returns **no decision** (never a fabricated `deny`: a deny arriving before the user answers reaches the agent as a decision they never made — issue #63) and pushes `permission-cleared` so clients drop the card. A registered SSE sync provider re-sends every pending prompt to each connecting client so ring-buffer eviction can never lose one, and emits an authoritative `permission-sync` id set that RETRACTS prompts that died while a client was offline. |
| `sessions.js` | Sessions map, PTY spawn/attach/kill lifecycle (via `pty.js`), ACP slot lifecycle (`registerAcpSession`/`endAcpSession`, including the transcript-path derivation that feeds the workflow scanner), session lookup helpers, snapshot, and ended-session pruning (ended slots stay in snapshots for `SESSION_PRUNE_GRACE_MS`, then get deleted). Its connect-time sync provider CLOSES with an authoritative `session-sync` frame listing every running slot, so a client can drop the sessions a restarted or crashed bridge no longer knows about — the additive per-slot re-send can never retract one (#66) — and each entry carries the slot's idle/working truth as a tri-state the `session` payload's present-only-when-true flag cannot express (#60). `ageOutZombieSessions()` sweeps beside the prune for slots stuck in `running` with nothing to vouch for them (#65): liveness evidence first (a live PTY process, a `registerSessionLivenessProbe()` verdict, a freshly written transcript), then a window — two minutes when a probe says the host is gone, twelve hours when only silence is available — and the result is a broadcast, REVIVABLE `ended` (reason `host-gone`/`no-liveness`), never a silent delete. |
| `codex.js` | All Codex integration: `~/.codex/sessions` JSONL scanner, TUI log monitor, synthetic exec-approval permissions, keystroke resolution into the Codex PTY. |
| `commands.js` | HTTP handlers for the watch-client API surface (`/pair`, `/command`, `/status`, `/ping`). |
| `admin.js` | HTTP handlers for the operator device-admin surface (`GET /admin/devices`, `POST /admin/devices/revoke`). Loopback-only, like `/acp/*` — operator-on-machine trust, no bearer; a LAN peer must not enumerate or disconnect paired devices. Lists devices by a short hash **prefix** id (never a token or full hash) and revokes one (`{id}`, prefix-matched — ambiguous prefix refused rather than guessing) or all (`{all:true}`). Revocation runs in-process because the running bridge owns the token set and rewrites `credentials.json` on every change (a separate CLI would race it); on revoke it also drops the affected device's live SSE stream. NOT part of the versioned `/v1` client protocol — see PROTOCOL.md "Admin surface". |
| `pty.js` | Platform-specific PTY spawning via the system `script` utility. |
| `acp.js` | The loopback channel to the forked `claude-agent-acp` Zed launches (`/acp/register`·`update`·`deregister`·`spawn-result`·`claim` + the held `/acp/inbox` SSE the bridge writes `inject`/`permission-decision`/`input-decision`/`spawn`/`close` frames down). Owns the session→connection routing, ACP turn state + prose coalescing, wrist-raised ACP permissions (#80; parked-even-with-zero-clients for detached watch-spawned sessions), wrist-raised AskUserQuestion cards (#111: the adapter's `input-request`/`input-resolved` frames reshaped into the hook-era question-card wire shape, positional answers back as `input-decision`, expired on session end), the watch-spawn correlation (`requestAcpSpawn`: explicit `spawn-result` ack, timeout → honest error, late success converges via the register announce with `spawnRequestId` attribution), the wrist kill (`requestAcpClose`, #88: a `close` frame relayed to the owning fork, settled ONLY by the session actually ending — so an unserviced frame times out as a refusal instead of faking #53's zombie), and the desk-pickup registry (`/acp/claim`: atomic newest-first take per cwd, retired by the attach-time re-register, survives fork death by design). Slot lifecycle stays in `sessions.js` (`registerAcpSession`/`endAcpSession`), including the liveness probe it registers there: a fork's held inbox is its sessions' proof of life, so an idle-for-days ACP thread is never aged out while a slot whose binding leaked past its fork's disconnect is. |

Dependency direction is strictly downward (`server.js` → handlers → sessions/codex → transport-sse → credentials → config → util; `rate-limit.js` sits beside `credentials.js` and imports only `config.js`; `host-guard.js` sits beside `util.js` at the bottom and imports nothing). Would-be cycles are broken with additive callbacks registered at module evaluation: `sessions.js` exposes `registerSessionCleanupHook()` (used by `codex.js` to clear synthetic permissions when a PTY dies) and `registerSessionLivenessProbe()` (used by `acp.js` to answer whether a fork still holds a session, so the zombie ageing can prefer evidence over a timeout), and `transport-sse.js` exposes `registerSseSyncProvider()` (used by `sessions.js`, `permissions.js`, and `codex.js` to contribute connect-time catch-up events). Consequence: `codex.js` must be imported for those registrations to happen — importing `sessions.js`/`transport-sse.js` in isolation (e.g. from an in-process unit test) yields a bridge without codex cleanup/sync wiring. The production entry point `server.js` always imports everything.

## HTTP surface policy

- **Legacy unprefixed routes (`/pair`, `/command`, `/events`, `/status`) are FROZEN.** Existing iOS/watchOS clients depend on their exact response shapes, status codes, log output, and timings. Do not change them. (The `/hooks/*` surface that once sat beside them was server-local, never client-facing, and was retired repo-wide in #87.)
- **Every route is also reachable under a `/v1` prefix** (e.g. `/v1/pair`): `server.js` looks up the exact path first, then falls back to the prefix-stripped legacy key, so today the two surfaces are byte-identical.
- **Protocol-shape changes** — per-device pairing, machine-readable permission semantics, richer session metadata, etc. — land on dedicated `/v1` handlers only: add an exact `"METHOD /v1/..."` key to the routes table and it wins over the fallback. Legacy clients keep the frozen behavior.
- **Behavior-internal hardening** (bug fixes with no observable protocol change, security tightening, performance) applies to both surfaces, since they share handlers until they are deliberately split.
- **ACP endpoints (`/acp/*`) are unauthenticated but loopback-only**: the Zed-launched fork calls them from this machine, so any non-loopback `remoteAddress` gets a 403 before the body is read (a LAN peer must not be able to register phantom sessions or spoof permission prompts onto the trusted watch UI). Permission state (`permissions.js`) is shared across surfaces: a decision posted on either client surface resolves a prompt raised on the uplink.
- **Auth contract:** tokens are per-device and are drawn from a single shared store — a token issued by either `/pair` or `/v1/pair` is valid on both surfaces, and legacy-issued tokens keep working everywhere. `requireAuth()` accepts a bearer token if its SHA-256 hash matches any stored credential (constant-time compare on the hash buffers). Pairing a new device never invalidates an existing one.
- **`GET /status` requires the bearer token** (a deliberate hardening exception to the legacy freeze: its session snapshot enumerates every project's absolute path, which must not be readable by arbitrary LAN peers on a 0.0.0.0 bind). Unauthenticated 401s with `{"error": "Unauthorized"}`.
- **Admin endpoints (`/admin/devices`, `/admin/devices/revoke`) are loopback-only operator tooling, NOT part of the versioned `/v1` client protocol** (`admin.js`): same operator-on-machine trust as `/acp/*` (no bearer; non-loopback → `403 {"error": "Admin endpoints are only accepted from localhost"}` — distinct wording from the ACP gate's 403). They list and revoke paired devices on the running bridge; watch clients never call them. See "Credential store & pairing lockout → Revocation" below and PROTOCOL.md "Admin surface".
- **`GET /ping` is the unauthenticated discovery probe.** Watch clients verifying a candidate bridge address — the localhost fallback, manual IP entry, or the Android emulator's `10.0.2.2` host alias — probe `GET /ping` instead of `/status`. It returns exactly `{proto, bridgeId, machineName}` (`proto` is the numeric protocol version, the same number the Bonjour `txt.v` advertises — see PROTOCOL.md "Versioning") and nothing richer; everything else stays behind auth.
- **Protocol versioning gate on `/v1/pair` only:** a `/v1` pair request must declare an integer `proto >= MIN_SUPPORTED_CLIENT_PROTO` or it is refused with `426 {error, proto, minProto}` before the pairing code is considered (no token minted, code not burned). The `/v1/pair` success response carries `proto` and — unlike the frozen legacy response — no top-level `sessionId` alias: on `/v1`, `bridgeId` is the only bridge-instance identity and `sessionId` always means an agent-session slot id (`handleStatus` drops the alias on `/v1/status` the same way). Legacy `/pair` performs no version check, forever.
- **Host-header allow-list (DNS-rebinding guard):** every request is checked pre-auth against an allow-list — `localhost`, loopback addresses, every local interface address (the bound LAN IP), and `10.0.2.2` (the Android emulator's alias for its host; without it emulator-based Wear clients could not reach a bridge on the same machine). The interface-derived entries are **not** a startup snapshot: a Host miss re-snapshots `os.networkInterfaces()` (throttled to once per second) and re-checks, so a bridge whose LAN IP changes mid-run (DHCP re-lease, network switch) keeps serving without a restart. Operators extend the static entries via `CLAUDE_WATCH_ALLOWED_HOSTS` (comma-separated env var) or repeatable `--allow-host=<host>` flags. Unknown or missing Host → `403 {"error": "Forbidden Host header"}`; a syntactically invalid Host keeps its frozen 400.

## Permission decision semantics (/v1 contract)

Approve/deny meaning is machine-readable end-to-end — clients never infer it from option position or English label substrings (which silently invert an approval into a denial when wording or ordering changes):

- **Every permission option carries `behavior: "allow" | "allow-always" | "deny"`.** `permission-request` SSE events (except `AskUserQuestion`, whose per-question option lists are content, not permission decisions) carry a top-level `options` array of `{behavior, label, description?}`. The ACP lane maps the agent's own options (`allow_once`/`allow_always`/`reject_*`) through `behaviorForAcpOption` in `acp.js`; the Codex synthetic exec-approval menu is built through the same `canonicalPermissionOptions()` normalizer, and its top-level `options` mirrors `tool_input.questions[0].options`. `canonicalPermissionOptions()` throws on a behavior-less option — nothing without machine-readable semantics is ever broadcast.
- **The decision endpoint accepts behavior-based answers.** `POST /command` / `POST /v1/command` with `decision: {behavior: "allow-always"}` (or the legacy iOS `allowAll: true` flag, normalized to the same behavior) reaches the ACP echo keyed on the behavior the user chose, so the agent receives its own `allow_always` option — never an allow-once masquerading as a standing grant (#110). Codex synthetic answers resolve `behavior` (or, for legacy clients, the echoed `optionIndex`/`selectedOption` looked up in the canonical option list the bridge itself broadcast) into TUI keystrokes: allow → `y`, allow-always → `2\n` (degrading to `y` when the menu has no trust entry), deny → Esc.
- **AskUserQuestion answers every question.** The event forwards ALL `tool_input.questions` (#111: the adapter mirrors its Zed form elicitation to the bridge); the decision carries `answers` (array aligned with the questions, or an object keyed by question text — accepted top-level or inside `decision`), which the bridge sends back down the inbox as a positional `input-decision` frame. The legacy single `selectedOption` path (first question only) stays frozen.

New fields on existing SSE event payloads are additive: legacy clients decode only the keys they know, so `options` on `permission-request` is invisible to them.

## Credential store & pairing lockout

**Store.** Paired-device credentials persist in `~/.claude-watch/credentials.json` (directory overridable via the `CLAUDE_WATCH_CREDENTIALS_DIR` env var — tests point it at per-test temp dirs so they never touch the real store). The directory is created `0700`, the file is written `0600` via an atomic temp-file + rename, and it holds only token *hashes* — the plaintext token is returned to the device at pair time and never stored:

```json
{
  "version": 1,
  "tokens": [
    {
      "hash": "<sha256 hex of the bearer token>",
      "deviceName": "watch-a",          // optional, from the pair request body
      "createdAt": "2026-07-03T00:00:00.000Z",
      "surface": "legacy"                // or "v1": which endpoint issued it
    }
  ]
}
```

The store is loaded at startup, so a bridge restart no longer unpairs anyone.

**Corrupt store fails closed.** If `credentials.json` *exists* but is unreadable, fails `JSON.parse`, or contains no valid token entries, the bridge starts with pairing **LOCKED** and logs a loud `SECURITY:` error — an attacker who can corrupt (not even read) the file must not be able to force a fresh pairing window. Recovery is an explicit operator action: restore or delete the file and restart, or restart with `--allow-pairing` (the next successful pair rewrites a fresh valid store). Only a genuinely *absent* store file keeps the fail-open first-run behavior (pairing open, code in the banner). A store with a mix of valid and invalid entries loads the valid ones and logs a warning about the rest.

**Pairing lockout.** After any successful pair (on either surface) the pairing surface locks: subsequent `POST /pair` / `POST /v1/pair` return `403 {"error": "Already paired. Re-pairing requires explicit authorization on the bridge."}`. A bridge that starts with a non-empty store starts locked (its banner shows `Pairing: locked (SIGUSR1)` instead of a code). Reopening is a scriptable operator action, never a client request:

- `SIGUSR1` — reopens pairing at runtime and mints a fresh code with the normal 5-minute TTL (logged exactly like startup: `Pairing code generated: ...`); the surface locks again after the next successful pair. A reopened window that expires *without* a successful pair **relocks** instead of regenerating a fresh code — an operator who reopens and forgets must not leave the surface open indefinitely (the pair attempt that observes the expiry gets a 403 and the lockout re-engages). The *initial* startup pairing window keeps the historical regenerate-on-expiry behavior (`401 Pairing code expired. A new code has been generated.`), preserving first-run UX.
- `--allow-pairing` — CLI flag; starts the bridge with pairing open even when devices are already paired (this startup window behaves like the initial one: expiry regenerates).

**Legacy freeze.** `/pair` keeps its frozen request/response JSON, status codes, and log lines. The invisible fix: success now *adds* a credential instead of overwriting the single global token (previously, re-pairing deauthenticated the current device). The 403 lockout is a new state the legacy flow could not meaningfully reach before — the old behavior silently reopened pairing after success, which is exactly the bug this replaces.

**Rate limiting.** Pairing attempts are limited per remote IP (`rate-limit.js`, 5 attempts per 5-minute fixed window per address), so one source exhausting its attempts cannot 429 a different source.

*Known limitation:* per-IP limiting is evadable by source-address rotation — an attacker on the LAN with IPv6 privacy/temporary addresses (or any pool of addresses) gets a fresh window per address, and conversely multiple legitimate clients behind one NAT share a single window. The rate limiter is a brute-force speed bump, not the primary defense; the primary defense is the default-locked pairing surface (locked whenever any device is paired or the store is corrupt, reopened only by explicit operator action, and auto-relocking when a reopened window expires unpaired).

**Revocation (operator device admin, issue #72).** Listing and revoking paired devices is a **loopback-only** operator surface on the *running* bridge (`admin.js`), gated exactly like `/acp/*` — operator-on-machine trust, no bearer. It lives on the running server, not a standalone CLI, precisely because the bridge holds the token set in memory and rewrites `credentials.json` on every change: a separate process editing the file would race it and be clobbered on the next pair.

- `GET /admin/devices` → `{devices:[{id, deviceName, createdAt, surface}]}`. `id` is the **first 12 hex of the SHA-256 hash** — a prefix that disambiguates and targets a revoke while keeping both the token and the full hash off the wire (the plaintext token is not even derivable from the full hash; the prefix leaks strictly less). Never returns the raw hash.
- `POST /admin/devices/revoke {id}` removes the device whose hash **starts with** `id`, persists, and returns `{ok:true, revoked:<deviceName|id>}` — never a token/hash. A prefix matching two or more devices is `400` with **nothing removed** (never guess which device); an unknown prefix is `404`; a missing/short/non-hex `id` is `400` (an empty prefix would otherwise match every entry and silently revoke the only paired device). The revoked token stops authenticating immediately (`requireAuth` no longer matches it), and its live SSE stream is dropped at once — each `/events` connection is tagged at connect time with the device hash it authed with, so a targeted revoke can end exactly that stream instead of waiting for its next authed request.
- `POST /admin/devices/revoke {all:true}` empties the store (`{version:1, tokens:[]}`), returns `{ok:true, revoked:<count>}`, and force-drops every live SSE stream (no token survives, so every open stream is now a revoked device). It deliberately does **not** reopen pairing — revoke-all is not a reopen, so the operator still uses `SIGUSR1` / `--allow-pairing`. **Restart note:** a cleanly-emptied store is a *well-formed empty* store, which the fail-closed loader (below) treats as corrupt — so a bridge restarted after revoke-all comes up **LOCKED** and logs a `SECURITY: ... (empty token list)` line. That is fail-closed-correct (an empty store must never silently reopen pairing); the "unreadable/invalid" wording simply overreads for this case. Re-pairing is the ordinary locked-store recovery. This keeps the empty-store-is-corrupt invariant (and its tests) untouched.

The surface is **not** part of the versioned `/v1` client protocol — it is server-local operator tooling (PROTOCOL.md "Admin surface (server-local, operator)"). The `/v1` prefix fallback makes `/v1/admin/...` resolve to the same handlers, harmlessly, still loopback-gated. Manual file surgery still works as a fallback (stop the bridge, edit or delete `credentials.json`, restart) — but do not edit the file while the bridge runs; use the admin surface instead.
